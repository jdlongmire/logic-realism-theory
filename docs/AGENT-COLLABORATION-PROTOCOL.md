# Perplexity Computer ↔ ThinxS Collaboration Protocol

**Version:** 1.0  
**Date:** 2026-03-23  
**Status:** Active

GitHub Issues are the shared communication layer between Perplexity Computer
(remote, cloud) and ThinxS (local, JD's machine). Neither agent calls the other
directly — all state is mediated through issues in this repository.

---

## Roles

| Agent | Runs on | Primary responsibilities |
|-------|---------|--------------------------|
| **Perplexity Computer** | Cloud (Perplexity) | Theory review, MMR, issue triage, proof drafting, task queuing |
| **ThinxS** | JD's local machine | Lean builds, proof validation, supplement writing, git operations |

---

## Issue Types and Ownership

### `[TASK]` — Work assignment from Perplexity Computer to ThinxS

**Created by:** Perplexity Computer  
**Labels:** `infrastructure` or `formalization` + `thinxs-action-required`  
**Structure:**

```
Title: [TASK] <verb> <object> — <claim ID or context>

Body:
## Objective
One paragraph: what to do and why.

## Instructions
Numbered, unambiguous steps.

## Inputs
Links or paths to everything ThinxS needs to read first.

## Expected Output
Exact files to create/modify, issue to comment on, commit message format.

## Acceptance Criteria
Checklist of what "done" means.

## Context
Link to originating MMR issue, claim ID, or session summary.
```

**ThinxS response:** Comment on the issue with result (see below), then close if complete.

---

### `[RESULT]` — Completion report from ThinxS to Perplexity Computer

**Posted as:** Comment on the originating `[TASK]` issue  
**Structure:**

```
## Result — <TASK ID>

**Status:** ✅ SUCCESS / ❌ FAILED / ⚠️ PARTIAL

**What was done:**
<brief prose>

**Outputs:**
- <file path or commit SHA>
- <file path or commit SHA>

**Build metrics (if lean_build):**
- Axioms: N (PRIMITIVE: N, EXTERNAL: N, REMAINING: N)
- Sorries: N
- Jobs: N
- Duration: Ns

**Errors / notes (if any):**
<error output or observations>

**Next:** <what Perplexity Computer should do next>
```

---

### `[MMR]` — Multi-model adversarial review

**Created by:** Perplexity Computer  
**Labels:** `multi-model-review`, `mmr:pass` or `mmr:fail`  
**ThinxS role:** None — MMR issues are Perplexity Computer ↔ JD only.  
ThinxS may be assigned follow-on `[TASK]` issues triggered by MMR failures.

---

### `[BUILD-REPORT]` — Lean build status

**Created by:** ThinxS (via lean_build_agent.py)  
**Labels:** `formalization`, `infrastructure`  
**Structure:** Auto-generated by `scripts/lean_build_agent.py`. Perplexity Computer
reads these at session start to get current build state.

## Labels for This Protocol

| Label | Meaning |
|-------|---------|
| `thinxs-action-required` | ThinxS must act — task is waiting |
| `thinxs-complete` | ThinxS finished — Perplexity Computer to review |
| `perplexity-action-required` | Perplexity Computer must act — awaiting proof revision etc. |
| `blocked` | Cannot proceed without external resolution |

---

## Task Queue vs Issues

**`theory/tasks.md`** handles automated, mechanical tasks (lean_build, lean_proof)
that ThinxS physics_agent.py polls and executes without reading context.

**GitHub Issues** handle tasks that require judgment, reading prior work, or
producing documents (supplements, theory sections, analysis).

Rule of thumb:
- If ThinxS needs to read something to do it → GitHub Issue
- If it can be fully specified in a task entry → `theory/tasks.md`

---

## Session Startup Protocol

### Perplexity Computer (start of each LRT session)
1. Check `docs/formalization/build-reports/LATEST.md` for current build state
2. Check open `[TASK]` issues labeled `thinxs-complete` for results to incorporate
3. Check `theory/tasks.md` for completed/failed tasks
4. Proceed with session work

### ThinxS (on daemon poll or manual trigger)
1. Check `theory/tasks.md` for pending `lean_build` / `lean_proof` tasks → execute
2. Check open issues labeled `thinxs-action-required` → work the oldest unblocked one
3. Post `[RESULT]` comment, update labels, close if fully resolved

---

## Commit Message Convention

ThinxS commits follow this format:

```
<type>(<scope>): <description>

<body — what was done and why>

Addresses: #<issue number>
Co-Authored-By: ThinxS <thinxs@local>
```

Types: `proof`, `build`, `docs`, `refactor`, `fix`, `feat`  
Scopes: `lean`, `theory`, `scripts`, `docs`

---

## Escalation

If ThinxS encounters something unexpected that blocks a task:
1. Post a `[RESULT]` comment with status `⚠️ BLOCKED`
2. Add label `blocked` to the issue
3. Describe exactly what is blocking and what information is needed
4. Perplexity Computer will read it next session and resolve or re-queue
